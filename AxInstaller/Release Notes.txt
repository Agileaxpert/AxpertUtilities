7) Execution of Data Migration SQL Scripts
AxInstaller executes data migration scripts based on the source version defined in config file.

If source version is 10.x
 → Executes: Data_Migration_10X.sql

If source version is 11.x
 → Executes: Data_Migration_11X.sql

These scripts are executed automatically during version upgrade, after the after_import_script.sql scripts.

Additional Manual Step for 11.x Upgrades:
For 11.x PostgreSQL environments using AXDEF schema, certain table data must still be migrated manually.
The installer adds these instructions to the Manual Action Required file.
Tables to be migrated manually:
axvarcore
axp_customdatatype
axpdef_language
tstructscripts
iviewscripts
The instruction file also includes the necessary SQL statements with schema placeholders such as:
{runschema} , {defschema} , {axdef}
Users must replace these with the appropriate schema names before execution.
Note: Migration SQL script files must adhere to the standard Axpert SQL formatting rules. Each SQL statement should be enclosed within << >> markers and must not end with a semicolon (;). 
For example, 
<<
insert into ....
>>

17) PluginAPI IIS Hosting Enhancement
AxInstaller is enhance to Automate IIS site creation and configuration during plugin installation
Deployment Flow.
Plugin API files are downloaded from Git and  are copied to:
	....\Arm_Agileconnect\ARM\AxPlugins\<ApiFolderName>
Physical path for hosting the Site is received as 'IIS Plugin Application Path' and stored in the appsetting.config file along with the other deatils of the schema.
To add the path use 'config new' or 'config edit' commands

->Existing Plugin API Handling
	-During plugin installation, AxInstaller copies the plugin API files from the downloaded plugin package to the corresponding Plugin API directory.
	-Existing files are overwritten if a newer version of the same file is available in the plugin package.
	-Files that are not part of the plugin package remain unchanged.
	-The installation process does not perform a complete cleanup of the existing Plugin API directory.

->IIS Configuration Logic
After the Plugin API files are deployed, AxInstaller automatically configures IIS for the plugin API under ARM site.The IIS Application name and Application Pool name are derived from the Plugin API folder name.The installer verifies :
	-Checks whether the IIS Site already exists.
	-Checks whether the corresponding Application Pool already exists.
	-Verifies that the IIS Site points to the expected physical path.
	
	Case 1 : If the Plugin API is already configured in IIS:
		-> AxInstaller verifies the IIS configuration.
		-> Existing IIS Application and Application Pool are reused.
		-> No duplicate IIS Applications or Application Pools are created.
	Case 2 : If Plugin API is new
		-> Application Pool and IIS Site is created.
		->Required folder permissions are assigned,Site and Pool are started.

->Application Pool Handling During Installation
The current implementation does not explicitly stop the IIS Application Pool before deploying files.Files are copied directly to the target Plugin API location.IIS configuration is then validated and updated as part of the installation process.
Naming Convention
    * IIS Application Name     	        = Plugin API folder name.
    * IIS Application Pool Name      = Plugin API folder name followed by "Pool".
	Example :
		1.Plugin API Folder	   -	AxiApi
		2.IIS Application	   -	AxiApi
		3.Application Pool	   -	AxiApiPool
Important Note 
->Stop IIS only when necessary. For most new plugin installations, stopping IIS is not required.
